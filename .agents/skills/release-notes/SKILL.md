> **Note:** In this repo all tooling runs via `nix develop -c ...`.

Draft the user-facing notes for the upcoming release. You are one step of the
release flow described in [docs/contributing.md](../../../docs/contributing.md)
(Release notes & CHANGELOG); the human polishes after you.

**Ownership rule (critical):** `CHANGELOG.md` is human-owned. Your edits to it
must be additive proposals shown as diffs for approval; never rewrite or delete
existing hand-written content, and never touch released sections. The raw
commit list lives in `tmp/release-notes-draft.md` (generated by
`just release-notes`) and is source material only.

**Steps**

1. **Ensure a fresh cliff draft**

   Run `nix develop -c just release-notes`. It writes the conventional-commit
   skeleton for everything since the last version tag into
   `tmp/release-notes-draft.md` (grouped Added / Fixed / Changed, one bullet
   per PR). Show it to the user.

2. **Collect context per entry**

   For every `(#N)` reference in the draft, fetch the issue/PR via
   `gh issue view N` / `gh pr view N` (title + body are enough). Look
   especially for consequences and implicit connections that are NOT visible
   from titles: what the change means for the end user, behavior switches,
   migration/compat notes.

3. **Read the hand-written highlights**

   Read `## [Unreleased]` in `CHANGELOG.md`. These entries were written right
   after each feature landed and often contain the "why it matters" prose.
   Treat them as authoritative seeds — do not paraphrase them away.

4. **Propose additions to `[Unreleased]`**

   Following the format fixed in docs/contributing.md (modeled on the 0.3.x
   sections):

   - Each line: `**Essence.** explanation`, English.
   - Add ONLY entries that matter to the end user; skip pure internals.
   - Prose is optional by design: if a release is all minor fixes, an empty or
     missing section is fine — do not invent filler.
   - Present additions as a diff against the current file and wait for
     approval. Apply approved edits verbatim.

5. **Remind about the version bump**

   Compare the latest `v*` tag with `src-tauri/tauri.conf.json` `.version`.
   If the next release requires a version bump, remind the user explicitly:
   both must be updated before tagging (`release.yml` fails fast on mismatch).
   Do not bump anything yourself.

6. **Summarize**

   Report: what was added to `[Unreleased]`, what was deliberately left out,
   and whether the version still needs a bump. Next steps belong to the human:
   polish, move `[Unreleased]` under `## [X.Y.Z] — date` at bump time, tag.
   Remind that after the tag's draft release appears, its body must be completed
   with the `## What's Changed` PR block and the Full Changelog link before
   publishing (docs/contributing.md, Release flow step 4).

**Guardrails**
- Never write to CHANGELOG.md outside an approved additive diff
- Never touch `tmp/release-notes-draft.md` contents as if they were final text
- Do not run `git tag`, bump versions, or modify `release.yml`
- All GitHub-bound texts follow the draft-approval rules (CLAUDE.md)
